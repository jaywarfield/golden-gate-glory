# **Mission Veteran AI** *by G3*

#### IBM Bob

##### The role IBM Bob played

IBM Bob was the primary development assistant for the entire project, used by all three team members throughout the competition window. The scope of what was built in a constrained timeframe — four toolkit packages, five watsonx Orchestrate agent YAML definitions, a FastAPI bridge server, seven Jupyter notebooks, twelve RAG knowledge bases, Terraform infrastructure scripts, a seven-screen single-page web application, Governance Factsheet and monitor registration, and all documentation — was only achievable because IBM Bob accelerated every stage of that work.

As stated directly in docs/problem.md:

```
  "IBM Bob delivered measurable team productivity gains: the entire project — seven agents, twelve RAG knowledge bases, Jupyter notebooks, Terraform infrastructure scripts, a FastAPI backend, and a seven-screen web UI — was designed, implemented, debugged, and documented by a three-person team using IBM Bob as the primary development assistant throughout. IBM Bob drafted code, caught logic errors, rewrote prompts, and produced this submission. Without IBM Bob, this scope of work would not have been achievable within the competition window — it multiplied what a small team could deliver."
```

##### What IBM Bob specifically built

BM Bob scaffolded all five YAML agent specs — agents/coordinator_agent.yaml, agents/accomplishment_translator_agent.yaml, agents/skill_mapper_agent.yaml, agents/gap_analyzer_agent.yaml, and agents/plan_builder_agent.yaml — including the multi-step coordinator instructions, the collaborator routing logic, and the boundary rules that prevent the agent from making hiring predictions, disclosing PII, or allowing export when the gate is blocked.

All four Python toolkit packages.

IBM Bob implemented the full logic for every tool in every toolkit:

- translate_accomplishment() — the strict no-fabrication military-to-civilian bullet translation prompt and its SKIP sentinel for inputs too vague to translate faithfully
- map_military_skills() — the O*NET crosswalk integration, the evidence-quote requirement, and the normalization guards for the multiple JSON shapes Granite occasionally returns
- analyze_skills_gap() — the bidirectional substring skill matching, lookup_skillsbuild(), and lookup_skillbridge() KB functions
- analyze_job_description(), build_resume_draft(), and evaluate_export_gate() — including the two-pass grounding check that downgrades unsupported EVIDENCED items to INFERRED and surfaces them as distinct grounding_warnings

The FastAPI bridge server

src/server.py — the bridge between the front-end and watsonx.ai — was generated by IBM Bob. It routes eight step names to their corresponding toolkit functions, handles mock vs. live mode, and returns consistent structured error responses so the front-end never crashes on a failed LLM call.

The seven-screen web UI

web/index.html — the entire single-file SPA — was authored by IBM Bob. This includes the step progress rail, the branch/specialty/career-path form controls, the accomplishment bullet inputs with live translation display, the gap analysis coverage table with colour-coded tier rows, the EVIDENCED/INFERRED/MISSING tagged résumé renderer, the export gate lock UI, and the full mock data layer that makes the application fully interactive even without watsonx.ai credentials.

Jupyter notebooks

All seven notebooks/ — NB 01 through NB 07 — were written by IBM Bob, covering bullet translation, skill mapping, job analysis, résumé drafting, materials building, gate control, and the authoritative end-to-end pipeline integration test.

Infrastructure and tooling

- terraform/main.tf, variables.tf, outputs.tf — the full IBM Cloud provisioning stack for watsonx Orchestrate and watsonx Governance
- Makefile — all build, deploy, test, and teardown targets including bridge-build, bridge-push, bridge-deploy, pages-secret, and bridge-logs
- Dockerfile and start.sh — the container definition and startup script with RAILWAY_PUBLIC_DOMAIN-based API_BASE injection
- governance/register_factsheets.py, factsheets.yaml — the Governance AI use case and monitor registration scripts
- knowledge-bases/ — all 12 RAG source JSON files

Every file in docs/ — technology.md, problem.md, rag.md, notebooks.md, governance.md, environment.md, and the architecture HTML diagrams — was written by IBM Bob. The architecture diagram footer reads: "Made with IBM Bob."  This includes the three visual deliverables created entirely in IBM Bob:

- docs/images/source/mission-veteran-ai-architecture.html — the full system architecture diagram showing all six deployment options, the GUARD/ORCH/AGENTS/GOV/RAG/OUTPUT layer stack, Terraform annotations, Governance tags, and all 12 RAG source cards. The file's own footer reads: "Made with IBM Bob."

- docs/images/source/mission-veteran-ai-environment-architecture.html — the environment and deployment-target architecture diagram, showing the split between local, Railway, Code Engine, OpenShift, and GitHub Pages, and how start.sh, API_BASE injection, and USE_MOCK wire them together. Its footer also reads: "Made with IBM Bob."

 - Slide 6 of mission-veteran-ai-final-presentation-textonly.pptx — the condensed architecture slide for the competition presentation deck, authored and iteratively updated in IBM Bob using the office_edit tool.

These are not code artifacts — they are polished, presentation-ready visual documents that required design judgment about layout, information density, labeling, and colour coding. Producing them in IBM Bob rather than a separate diagramming tool kept the entire project — code, documentation, diagrams, and presentation — within a single development environment.

##### Why including IBM Bob is a strong signal

1. It is the honest account of how the project was built. IBM Bob was the actual development environment used for the entire project. It appears in GETTING_STARTED.md as a formal setup section — with instructions for downloading, logging in, activating a subscription, configuring the workspace, resetting it, and sharing it across team members. It is not mentioned as a tool that was used once; it is presented as the team's primary IDE.

2. It demonstrates IBM Bob's capability ceiling. A solution of this complexity — multi-agent coordination, grounding checks, Governance integration, IAM-based REST inference, six deployment targets — built by a three-person team in a competition window, is a concrete data point about what IBM Bob enables. The scope is the evidence.

3. The productivity argument maps directly to the veteran outcome. docs/problem.md makes this connection explicit: the same AI-multiplied productivity that let a small team build a complex system in a short window is precisely what Mission Veteran AI delivers to a veteran — compressing weeks of manual crosswalk research, gap analysis, and résumé drafting into a single session. IBM Bob and IBM Granite are solving the same class of problem at different scales.

4. It is an IBM product used in an IBM hackathon. Using IBM Bob as the development assistant for a solution built on watsonx Orchestrate, watsonx.ai, watsonx Governance, IBM Granite, IBM Code Engine, Red Hat OpenShift, and IBM SkillsBuild means the entire stack — from the AI model to the development tool to the deployment platform — is IBM. That coherence is intentional and meaningful for a competition evaluating IBM technology adoption.

5. The GETTING_STARTED.md instructions enable other IBM Bob users to reproduce the work. The setup, reset, and workspace-copy instructions are practical and specific. They show that the team understood IBM Bob well enough to document it for others — which is a different level of engagement than simply using it once.
